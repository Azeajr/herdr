Herdr はペインをバックグラウンドサーバーで動かし続けます。ターミナルクライアントはデタッチして、あとで再接続できます。

ローカル、SSH、`herdr --remote` の各ワークフローについては [Herdr での作業の進め方](/ja/docs/how-to-work/)を参照してください。

## デタッチと再アタッチ

`ctrl+b q` でクライアントをデタッチします。ペインとエージェントは動き続けます。再度 `herdr` を実行すると再アタッチします。セッションとそのペインを停止するには `herdr server stop` を使います。

サーバーの完全停止後に Herdr が再起動すると、保存されたセッションの形を復元します。デタッチ、サーバー再起動、画面履歴リプレイ、エージェントネイティブのセッション復元、ライブハンドオフでそれぞれ何が生き残るかは[セッション状態と復元](/ja/docs/session-state/)を参照してください。

## 名前付きセッション

独立した Herdr サーバーが欲しいときは名前付きセッションを使います。

```bash
herdr session list
herdr session attach work
herdr session attach side-project
herdr session stop work
herdr session delete side-project
```

名前付きセッションは独自のペイン、タブ、ワークスペース、ソケット、ランタイム状態を持ちます。グローバル設定ファイルは共有されます。

スクリプトでは `--json` を使ってください:

```bash
herdr session list --json
herdr session stop work --json
herdr session delete side-project --json
```

## SSH 越しのリモートアタッチ

リモートモードは 2 つあり、[Herdr での作業の進め方](/ja/docs/how-to-work/)で比較しています。tmux スタイルの方法では、サーバーに SSH してそこで `herdr` を実行します。もうひとつは、ローカルマシンから SSH 越しにアタッチする方法です:

```bash
herdr --remote workbox
herdr --remote ssh://you@server:2222
```

このモードでは、ローカルの Herdr はシンクライアントです。SSH 越しに接続し、リモートの Herdr サーバーを起動またはアタッチして、UI をローカルターミナルにストリーミングします。クライアントがローカルで動くため、Herdr は画像クリップボードの貼り付けのようなローカルデスクトップ機能をリモートセッションにブリッジできます。画像をリモートの一時ファイルにコピーし、そのパスを貼り付けます。

デフォルトでは、`herdr --remote` はそのアタッチにローカルの Herdr キーバインドを使います。リモートサーバーの設定が異なっていても、ローカルの操作感覚を維持できます。ローカルキーバインドはアタッチ時のスナップショットなので、ローカルのキーバインドを編集したらデタッチして再アタッチしてください。リモートサーバーの設定を使いたい場合は `--remote-keybindings server` を使います。ローカルのカスタムコマンドキーバインドは送信されません。それらのコマンドはリモートホスト上で実行されてしまうからです。

繰り返し接続する相手は SSH config を使ってください:

```text
Host workbox
  HostName server.example.com
  User you
  Port 2222
```

その後はこれでアタッチできます:

```bash
herdr --remote workbox
```

リモートアタッチは、Linux、macOS、Windows のローカルクライアントから、x86_64 と aarch64 の Linux および macOS ホストへの接続をサポートします。Herdr はリモートのプラットフォームを確認し、リモートの `PATH` 上にある一致する `herdr` を優先してから、一般的な直接インストール、Homebrew、mise、Nix プロファイルのパスを確認します。一致するバイナリがない場合、対話的な実行では `~/.local/bin/herdr` へのインストールを提案します。非対話的な実行はホストを変更せずに失敗します。`~/.local/bin` がリモートの `PATH` にない場合、Herdr はインストール後に警告します。Windows をリモートホストとして使うことはできません。

デフォルトでは、`herdr --remote` はユーザーの SSH config を最初に include し、その後にフォールバックのキープアライブ設定を加えた一時的な SSH config を通してリモートセットアップとブリッジを実行します。既存のユーザーのキープアライブ設定が優先されます。Linux と macOS クライアントは接続再利用用のプライベートなアタッチ単位コントロールソケットも使いますが、Windows OpenSSH では使いません。Herdr が生成する設定やコントロールソケットを使わず通常の `ssh` を使うには `[remote].manage_ssh_config = false` を設定してください。

デフォルトでは、実行中のリモートサーバーの置き換えや再起動が必要な場合、リモートアタッチは通常の再起動/停止フローを使います。対応する実行中リモートサーバーで実験的なライブハンドオフにオプトインするには `--handoff` を渡します:

```bash
herdr --remote workbox --handoff
```

先にサーバーへ SSH してそこで `herdr` を実行した場合、Herdr は完全にサーバー上で動きます。このモードは便利でシンプルですが、通常のターミナルテキスト貼り付けを超えてローカルデスクトップのクリップボードにはアクセスできません。

ローカルとリモートのプラットフォームが一致する場合、直接インストールでは Herdr は現在のローカルバイナリをコピーできます。Homebrew、mise、Nix のインストールの場合、またはプラットフォームが異なる場合は、`https://herdr.dev/latest.json` から現在のクライアントバージョンに一致するリリースアセットをダウンロードします。

ローカルビルドやカスタムバイナリの場合は、リモートアタッチの前に `HERDR_REMOTE_BINARY` にローカルファイルパスを設定してください。

```bash
HERDR_REMOTE_BINARY=target/release/herdr herdr --remote workbox
```

## リモートの名前付きセッション

リモートホスト上の名前付きセッションにアタッチするには、`--remote` と一緒に `--session` を使います:

```bash
herdr --remote workbox --session agents
```

## ピアサーバーの連携

`herdr --remote` は自分のセッションを相手のセッションに置き換えます。ピアはもう一方の形です。自分の Herdr サーバーが別の Herdr サーバーに接続し、その相手のワークスペースを自分のワークスペースと並べて表示します。ひとつのサイドバーで複数マシンの作業をまとめて扱えます。

ピアはサーバーごとに設定し、再起動をまたいで保持されます。ピアはあくまで接続であり、ペインを移動させることはありません。それぞれのマシンが自分のターミナルを所有し、実行し続けます。

### ピアを追加する

同じマシン上のピアは API ソケットのパスで指定します:

```bash
herdr peer add beta --socket /home/you/.config/herdr/sessions/beta/herdr.sock
```

別ホスト上のピアは SSH の宛先で指定します。必要ならそのホスト上の名前付きセッションも指定できます:

```bash
herdr peer add workbox --ssh workbox --peer-session agents
```

フラグは `--session` ではなく `--peer-session` です。`--session` は *あなた自身の* どのサーバーに対してコマンドを送るかを選ぶもので、すべての `herdr` コマンドが受け付けます。

同じ 2 つのピアを[ソケット API](/ja/docs/socket-api/) から追加する場合:

```json
{"id":"1","method":"peer.add","params":{"name":"beta","target":{"type":"socket_path","path":"/home/you/.config/herdr/sessions/beta/herdr.sock"}}}
{"id":"2","method":"peer.add","params":{"name":"workbox","target":{"type":"ssh","destination":"workbox","session":"agents"}}}
```

SSH の宛先は `herdr --remote` とまったく同じように SSH 設定を使います。`herdr --remote` と違い、ピアはリモートホストの Herdr をインストールも置き換えもしません。バックグラウンドのサーバーは、別のマシンへ書き込む許可をあなたに求められないからです。リモート側にはあらかじめ一致する Herdr のビルドが必要です。確認を求めてくれる `herdr --remote <destination>` で一度インストールしてから、ピアを追加してください。

SSH ピアの接続は、見ている間だけでなくピアが設定されている限り保持されます。ピアを外すと接続も切断されます:

```bash
herdr peer remove workbox
```

`herdr peer list` はすべてのピアを、その接続先、接続状態(`connecting`、`connected`、`reconnecting`、`error`)、報告されたワークスペースの数とともに表として出力します。`reconnecting` と `error` は意味が異なるので区別する価値があります。`reconnecting` はまだ再試行中、`error` は諦めた状態で、再試行中のピアには試行回数が付きます。`--json` を付けると、ピアのバージョン、プロトコル、ワークスペースそのものを含む完全なレコードが得られます。`add`、`remove`、`list` はいずれもピアの一覧全体を返すので、どれを使っても結果を確認できます。

### ピアのワークスペースを開く

サイドバーのピアのヘッダーを右クリックし、**Open workspace...** を選ぶと、そのピアが報告したワークスペースを一覧できます。ヘッダーには `開いている数/全体数` のカウントが付くので、開く前に開けるものがあるか分かります。すでに開いているエントリには印が付き、それを選ぶと二つ目を開かずに既存のビューへ切り替えます。

`peer list` で得た id を使えば、コマンドラインや API からも同じことができます:

```bash
herdr peer open <instance-id>:w1 --focus
```

```json
{"id":"3","method":"peer.workspace.open","params":{"target":"<instance-id>:w1","focus":true}}
```

ターゲットはワークスペース id、ペイン id、ターミナル id を受け付けます。ピア一覧から得た id はピアのインスタンス id で名前空間化されており、それだけでピアを特定できます。ピア名も指定する — コマンドラインでは `--peer`、API では `name` — のは、ターゲットがピアローカルの素の id のときだけです。

ピアのワークスペースを開くと、中身はピア由来でありながら *ローカルな* ワークスペースが作られます。レイアウト、フォーカス、サイズはあなたのものです。ピアは、あなたのレイアウトが与えたサイズでターミナルを描画します。閉じてもピア側は動き続けます。

ピアが背後にあるペインを分割すると、分割は**ピア側で**行われ、その新しいペインへの二つ目のビューが開きます。そうして作られたペインは、あなたが要求したものなので、ビューを閉じるとピア側でも閉じられます。ピアが元から持っていたペインへのビューは、ピア側で閉じられることはありません。

接続が切れても、ペインはピアの最後の画面を暗く表示したまま、戻ってくるのかどうかを 1 行で示します — `reconnecting to <peer>… (attempt N)` または `disconnected from <peer>: <reason>` です。ピアに再び到達できるようになれば自動で再接続します。そのペインがもう存在しないとピアが答えた場合 — そこで `exit` を入力した、あるいは向こう側で閉じた場合 — ペインはローカルでも閉じられます。そのプロセスがこのマシンで終了したときとまったく同じです。グレーの `disconnected` 状態は、ピアに到達できない場合や、ピアが別のサーバーに入れ替わった場合にだけ残ります。

### ピアが背後にあるペインでできること

ピアが背後にあるペインは、自分のターミナル状態を持ちません。画面はピアが所有し、描画済みのセルを送ってきます。それが何が動くかを決めます:

- **入力、リサイズ、マウスホイール**は動きます。ホイールはピアのスクロールバックをスクロールし、ピアが実行中プログラム自身のホイール挙動を適用します。
- **`pane.read` は動き**、ピアが応答します。ピアに到達できないときは、空の画面を返すのではなく、ピアの状態を示す `unavailable` で失敗します。
- **スクロールバーはありません**。スクロール位置はピア側にあるからです。
- **コピーモードは開きません。** 選択と検索はローカルの画面を読みますが、それはここにありません。何も見つからないコピーモードを開く代わりに、Herdr はその旨を伝えます。
- **`agent.read` は動き**、`pane.read` と同じ理由でピアが応答します。
- **`agent.explain` は動きます。** 実際にルールを実行したピアが答えます。返ってくる説明には `peer` フィールドとピア側のペイン ID が付きます。そこに含まれるマニフェストのソース、バージョン、ルール ID は、手元ではなくピア側のインストールのものだからです。`herdr agent explain` はこれをマニフェスト行の上に `peer:` の行として表示します。

### ピアがそのペインについて報告するもの

ペインの作業ディレクトリ、ターミナルタイトル、エージェントもローカルでは読めないため、画面と一緒にピアから届きます。それらはローカルのペインと同じ場所 — `pane.get`、`pane.list`、`agent.list`、`agent.wait`、サイドバー、ワークスペース自身のステータス — に現れ、ピアのエージェントが working から idle になったことも、ローカルのエージェントと同じように伝わります。

更新は約 1.5 秒以内に行われるため、ピアのペインはローカルのものより一瞬古く見えることがあります。接続が切れた場合は空にせず最後のラベルを保持し、ピアが戻れば再び更新されます。

`pane.get` と `pane.list` はそうしたペインに `peer` を報告するので、クライアントは失敗を一つずつ踏まなくても違いを判別できます。

## ダイレクトターミナルアタッチ

完全な Herdr アタッチはワークスペース UI 全体を開きます。ダイレクトアタッチは、サーバーが所有するターミナルをひとつだけ、現在のターミナルに開きます。

ダイレクトターミナルアタッチは Windows では Unix 専用です。

エージェントターゲットでアタッチ:

```bash
herdr agent attach reviewer
```

ターミナル ID でアタッチ:

```bash
herdr terminal attach term_abc123
```

ダイレクトアタッチは、現在レンダリングされているターミナル状態をストリーミングし、その後ライブの ANSI フレームを流します。入力はそのターミナルに直接送られます。

`ctrl+b q` でデタッチします。リテラルの `ctrl+b` は `ctrl+b ctrl+b` で送ります。

ひとつのターミナルの入力とリサイズを所有できる書き込み可能なダイレクトアタッチクライアントはひとつだけです。既存の所有者を置き換えるには `--takeover` を使います:

```bash
herdr terminal attach term_abc123 --takeover
```

## シングルプロセスの逃げ道

バックグラウンドのサーバー/クライアント分離なしで Herdr を実行するには `--no-session` を使います:

```bash
herdr --no-session
```

これは主にデバッグや互換性のための逃げ道です。デフォルトの永続セッションモードが通常の使い方です。
